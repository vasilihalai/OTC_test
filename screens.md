# xRuby OTC — screens.md

Reverse-documented from the current implementation (`~/Desktop/untitled folder/OTC`), last brought in line with the code on 2026-11-04. §1–§7 describe what's actually built and live, not a design intent — use them as the baseline for the next round of changes. §8 opens with the open items, then keeps the change history in order; where an older history entry disagrees with a newer one or with §1–§7, the newer text wins.

## 1. Scope

Telegram Mini App (React + TypeScript + Vite, HashRouter, zustand). Mock-first: every screen reads/writes through `src/api/index.ts`, which resolves each function to either `src/api/mock/*` or `src/api/real/*` behind `VITE_USE_REAL_API`. **`api-integration.md`'s entire numbered work plan (§9) is now implemented against `real/*`** — auth, profile, balances, both withdrawal halves, account transfer, the certificate download, and the full OTC read/write/polling path (deals never stay mock-only behind the flag any more; `mockActions.expireQuote` is the one deliberate exception, a client-only countdown-driven state change with no server command to mirror). The test bot "XRuby OTC Test" (`otc-miniapp.dev.xruby.kg`) runs this in real mode against the dev gateway: sign-in, profile, balances and the deal screens have been exercised there and corrected (§8). Anything not yet seen on dev stays built to the doc's literal contract, flagged per-module where the doc itself flagged an open question (the `B1`–`B13` codes threaded through code comments and §8 below). Each round is verified via `tsc`/lint/build plus Playwright in mock mode and on stubbed real responses; the dev stand isn't reachable from the development environment, so checking there takes a DevOps rebuild and a person in Telegram.

**Auth has been rebuilt three times now — see §5 for the current shape, this is just the timeline.** Round 1: a Telegram-initData-binding flow (`session.start`/`login`/`login-confirm`/`logout`) per an early spec document, `initData` itself the credential, sign-in only ever appearing once per device — deleted (`real/session.ts`, `LoginConfirmModal`, an `AuthError` boot-blocking screen, `bootRealSession`, the personal/business two-different-backends `config.ts`). Round 2, against `api-integration.md` §0/§2: ordinary email+password+OTP on every app open, a real refresh token, `initData` demoted to a one-shot push-binding header — explicitly *not* an auth mechanism. Round 3 (current): the backend team gave a concrete, different, real contract — a genuine Telegram-identity-binding endpoint again (conceptually closer to round 1, mechanically different), silent re-entry once bound, no refresh token at all for this client. `initData`'s one-shot push-binding header from round 2 is gone along with it. Each round was a full replacement, not an extension — confirmed with the user before touching code each time, since every round invalidated real work the previous one had done.

Dark theme only, regardless of the user's Telegram theme — Profile's theme/language pickers are cosmetic (see §6.9), they don't switch anything.

### 2.3 Layout model — full-bleed panels, not inset cards

This is the thing most likely to regress, so it's stated first. A panel on Home, the withdrawal screens, and Profile is **390-ish wide at x=0, no side margin, ever** — the inset lives entirely in the panel's own `padding`. `Panel` (`src/components/Panel/Panel.tsx`) takes `fill` (`page | raised | surface`), `radius` (CSS shorthand — rounded only on the seam-facing edge(s)), and `padding` props; it never takes a margin. Screens that need this stack panels with `gap: 16px` in a flex column and let each panel's own background show through the gap — that 16px gap *is* the seam.

- **Home**: root `display:flex; flex-direction:column; gap:16px; background: var(--bg-surface)`. Three panels, **all sharing the same 16px radius now** (hero and deposit-account were `24px` — explicit "make the card corners one consistent radius" instruction, the mismatch was most visible where the hero panel's bigger curve sat directly behind the two 16px `StatCard` boxes nested inside it): hero (`radius="0 0 16px 16px"`, `padding="8px 16px 20px"`, bg-page), recent-deals (`radius="16px"`, `padding="20px 0 4px"`, bg-page, heading/rows carry their own 16px horizontal inset), deposit-account (`radius="16px 16px 0 0"`, `padding="20px 0"`, bg-page, same pattern).
- **Deals**: no panel at all — frame is bg-page, title/filter-chips/rows sit directly on it, rows full-bleed to both screen edges.
- **DealDetail**: no panel either — frame bg-page, header/quote-card/hold-confirmation/`Детали`/`Документы` sit directly on it at a flat 16px inset. `Детали` and `Документы` are **plain heading + rows, not cards** — an earlier version wrapped them in a `--bg-surface` card, which doesn't match; only the quote card and `RequisitesPanel` are genuine cards (`Panel fill="surface" radius="16px"`).
- **Withdrawals** (WithdrawCrypto/WithdrawFiat/WithdrawRequisites): single implicit full-bleed panel — content inset 16px horizontal, 20px top, 16 or 32px bottom depending on screen, no radius (it's the only content on the screen, so the frame color is never actually visible).
- **Profile**: two full-bleed panels (`padding: 8px 16px 24px`, radius `0 0 24px 24px`, then `16px`, radius `24px 24px 0 0`), `--bg-surface` frame, 16px seam, panel2's `Тема`↔`FAQ` divider is inset 24px (8 more than the row content) — that's drawn intentionally, not a bug.

**Row components reach both edges themselves.** `DealRow` (128px, used on Home and Deals) and `TableRow` (64px asset row, used on Home's deposit-account list) are full-bleed with their own internal padding — never wrapped in a padded container that would double the inset. `TableRow` is a 3-cell flex row: info-cell (`padding-left:16px`, holds `CurrencyIcon` + ticker/name), amount-cell, action-cell (68px wide, `padding-right:16px`, holds a 36px round `--bg-elevated` circle) — so the currency icon and the withdraw button both sit exactly 16px from the screen edge, symmetric. `DealRow` carries **no per-status background highlight** — a `RATE_ACTIVE` full-bleed highlight was tried, then explicitly reverted: it read as "the first item in the list is highlighted" rather than status-driven, which was confusing rather than informative. Its `.deal-row__id` text is **16/24, weight 500**, measured from the frames.

### 2.4 Motion — page transitions, modal open/close, loading

Reverse-documented after an explicit "go through the whole app, make every transition and loading state smoother, with nicer loaders" pass. The rule this pass settled on: **every overlay that animates in now also animates out**, and every loading affordance uses the same shimmer/spin visual language rather than each screen inventing its own.

- **Route/page transitions** (`.app-content__page`, `src/index.css`) — every screen mount still just fades + slides up 10px (`page-in`, was 6px/`ease-out`/0.18s), no exit animation (React Router's `key`-based remount unmounts the old page synchronously — a true crossfade would need to keep both pages mounted during the swap, judged not worth the complexity for a screen-to-screen nav in a HashRouter mobile app). The curve is now `cubic-bezier(0.2, 0.8, 0.3, 1)`, the same easing `Modal`/`PickerModal`/`TransferModal` already used for their entrances — one motion signature for the whole app instead of a plain `ease-out` that only page transitions used.
- **Modal / PickerModal exit animations** — both used to `return null` the instant `open` went false, so their entrance animation (fade+scale, fade+slide-up) had no closing counterpart: the overlay just vanished on the same frame. Fixed via a new shared hook, `useDelayedUnmount(open, exitDurationMs)` (`src/lib/useDelayedUnmount.ts`) — keeps the node mounted for `exitDurationMs` after `open` flips false so a CSS closing animation has time to play, then unmounts. Both components add a `--closing` modifier (`e('card', { closing: !open })` etc.) while in that window: `Modal` gets `modal-scrim-out`/`modal-card-out` (fade + scale to 0.96/translateY 4px, 0.16s `cubic-bezier(0.4, 0, 1, 1)` — an "ease-in" curve, since something leaving should accelerate away rather than ease out like something arriving), `PickerModal` gets the sheet-equivalent (fade + slide back down to `translateY(24px)`, same timing). Every modal in the app rides on these two shared components (`AuthenticatorModal`, `VerificationModal`, `OtpConfirmModal`, `TransferModal`, `ConfirmDialog` all wrap `Modal`; Profile's Язык/Тема pickers use `PickerModal`), so this one fix closes the "modal just disappears" gap everywhere at once. `QrScannerModal` was deliberately left out of this — it's a live camera overlay, and tearing down `getUserMedia` promptly on close matters more there than a pretty fade.
- **Skeleton** (`src/components/Skeleton/Skeleton.tsx`) — swapped the plain opacity pulse (`0.5↔1`, 1.2s) for a shimmer sweep: a `linear-gradient(100deg, --bg-surface 33%, --bg-elevated 50%, --bg-surface 67%)` animated across a `300% 100%` background-size, 1.6s ease-in-out loop. Reads as a much more "designed" loading state than a fade, and is the standard skeleton pattern most apps use now. One shared component, so this landed on every screen that shows skeletons at once (Home, Deals, DealDetail, WithdrawCrypto, WithdrawFiat, Profile) with no per-screen changes needed.
- **Spinner** (`src/components/Spinner/Spinner.tsx`, new) — the small `currentColor` ring spinner `Button`'s `loading` state already drew inline (`.button__spinner`) was pulled out into its own reusable component so other places needing a spinner don't hand-roll the same CSS again. `Button` now renders `<Spinner size={20}/>` instead of its own `<span>`; `Button.css`'s spinner rule/keyframe moved to `Spinner.css` (renamed `button-spin` → `spinner-spin`) since nothing else in `Button.css` needed it.
- **Button `loading` consistency audit** — two confirm buttons (`WithdrawCrypto`, `WithdrawRequisites`) disabled themselves during `submitting` but never passed `loading`, so tapping "Подтвердить" gave zero visual feedback while the withdrawal request was in flight (every other confirm/submit button in the app — SignIn, NewPassword, PasswordRecovery, DealDetail's actions — already did this correctly). Both now pass `loading={submitting}` alongside their existing `disabled` conditions.
- **OTP verification spinner** — the three code-entry modals (`VerificationModal`, `AuthenticatorModal`, `OtpConfirmModal`) disable `CodeInput` while `verifying`/`confirming` (that flag stays true through both `verifyCode()` *and* the awaited `onVerified()` callback, i.e. the actual withdrawal/login submission that runs after the code checks out) but showed nothing to indicate work was happening — cells just went inert. Each modal now shows a small `<Spinner size={16}/>` + "Проверяем код…" (`ru.verification.verifyingLabel`, new) directly below `CodeInput` while that flag is true, fading in over 0.15s.
- **Amount-field thousands grouping while typing** — see §3's `AmountField` entry.

Labels are 14/20 `--text-muted`.

Replaces the old `<div>xRuby</div>` on SignIn and PasswordRecovery — two earlier attempts (plain red text, then a CSS-built badge+wordmark approximation) were both replaced once the actual brand SVG was supplied. Fixed colors baked into the SVG paths (white wordmark, `#C51625` mark) rather than tokens, since it's a literal asset, not a themed component.
- **AmountField** — label/available row, then a box (12px horizontal padding, matching TextField) with an optional embedded asset `Select`, the numeric input, and a "Макс" button. The old `transferVariant` (76px tall box, 28px input) was removed — the transfer modal's amount field now uses the same 44px sizing as every other field, per an explicit "make it match the standard fields" request. **The input groups thousands/millions live as you type** ("на всех экранах отделяем пробелом 3 разряда" turned out to still be missing from the one place numbers are actually *typed*, not just displayed — `formatAmount()` already covered every read-only display). The field stays a plain controlled `value`/`onChange` pair from the outside — `onChange` still fires with a clean `Number()`-parseable string, no spaces — the NBSP grouping is purely a display transform applied to what the `<input>` shows (`formatAmountInput()`/`sanitizeAmountInput()`, `lib/money.ts`; the same NBSP character `formatAmount()` uses, so a grouped `"1 234 567"` mid-typing and `"1 234 567.00"` once submitted look identical). `sanitizeAmountInput` also treats `,` as a decimal point, since Cyrillic keyboards' numeric layout produces a comma there — a small extra fix that fell out of needing sanitization anyway, not a separately-requested feature. Re-grouping a controlled input's displayed value on every keystroke moves the caret to the end by default (React has no way to know "the same digit" moved), so `AmountField` restores it itself: on each `onChange` it counts how many digits/decimal-points sat before the caret in the *old* string, then after the re-render finds the position after that many digits/decimal-points in the *new* (regrouped) string and calls `setSelectionRange` there (`useLayoutEffect`, so it lands before the browser paints) — typing or inserting a digit in the middle of a long number keeps the cursor sitting next to the digit you just typed, even as separator spaces shift around it.

A `trailingIcon` prop briefly existed (decorative `×` + chevron pair, only in the readonly state) for `RequisitesPanel`'s network field — removed again once that field became a real picker (see below) and the chevron took that slot back over; the prop had no other caller, so it and its CSS came out rather than staying as unused surface area. **The box's base fill is `transparent`; only the transfer modal's account selects and `RequisitesPanel`'s read-only selects override it, with `--bg-elevated`.** It's been through several rounds: `--bg-surface` → `--bg-raised` (per a WithdrawCrypto-specific Figma annotation) → transparent again once WithdrawFiat's own reference showed the opposite — at that point WithdrawCrypto and `RequisitesPanel` kept scoped `--bg-raised` overrides locally, since their own references still wanted a visible fill. `/login` (business) is the default sign-in route, `/login/personal` the alternate — a deliberate, standing deviation from generic nav conventions, made explicitly at the user's request; do not "fix" this back to a personal default.

**Both are `headerVariant: 'close'`, never `'back'`.** `/login/personal` used to be `'back'`, so toggling personal ↔ business made the header (and the native BackButton) flicker between close and back depending on which variant you landed on — wrong regardless of direction, since business and personal are two faces of one entry screen, not a parent/child pair with real navigation depth between them. Combined with the `replace`-navigation above, the two variants now behave as one screen for every purpose that matters (header, native back button, history) even though they're still two route paths internally.

**The personal/business switch links navigate with `{ replace: true }`, not a push.** They previously pushed a new history entry each time, so toggling personal → business → personal a few times left a long chain of login-variant entries in the browser/Telegram back-stack — pressing back would step through login variants instead of leaving the auth flow. Any "switch between sibling views of the same screen" link (as opposed to "go deeper") should follow this pattern: `replace`, not `push`.

AppHeader only renders when `isRealTelegram` is false (or `VITE_FORCE_INAPP_HEADER=true`) — inside a real, correctly-detected Telegram launch, Telegram's own native BackButton is used instead. The clearance `.app-content` reserves for it is measured live off the pill's rendered height (`AppHeader.tsx`'s `useHeaderClearance`, via `ResizeObserver`) plus a small fixed gap — tightened this round from a 28px gap/100px fallback down to a **2px gap / 48px fallback**, so the screen title sits almost immediately under the pill instead of leaving a visibly large empty band at the top.

**The native BackButton (`telegram/backButton.ts`'s `useAppBackButton`) only shows for `headerVariant: 'back'` routes, never `'close'`.** It used to show for both, which meant `/login` and `/otc-unavailable` — genuine entry points, nothing to go back to, even right after signing out — got Telegram's native back chevron anyway; tapping it did `navigate(-1)`, stepping back into whatever screen preceded the entry point (the session guards on those screens redirect straight back to `/login`, so this wasn't exploitable, but it read as a real navigation escape and shouldn't have been offered at all). `'close'` routes now leave the native BackButton hidden so Telegram's own default close affordance shows instead — there is no native "close" button we can render ourselves, only show/hide on the back one, so `'close'` semantics are "hide ours and let the platform's default take over," not a different button we draw.

**In real Telegram (no pill of our own), the fallback clearance is a live `calc()` expression, not a one-time computed number.** This fixed a real bug: that branch is keyed on `active`, which never changes across in-app navigation once we're in real Telegram, so its effect only ever runs once per cold load — and on cold load Telegram hasn't necessarily reported its safe-area insets yet. Baking `getComputedStyle(...)` into a plain px number at that moment could snapshot 0, and every screen navigated to afterward inherited that stale value (only a full reload re-ran the app late enough for the real inset to be available, which is why "content jams under the status bar on navigation, but is fine after reload" was the reported symptom). Writing `--header-clearance` as `calc(48px + max(var(--tg-viewport-safe-area-inset-top, 0px), var(--tg-viewport-content-safe-area-inset-top, 0px)))` instead keeps it correct forever — the browser re-resolves the `var()` references live whenever Telegram updates them, no JS re-run required.

**Every screen's own top padding is now a uniform 8px**, on top of that shared header clearance. It had drifted apart per-screen (Deals 4px, DealDetail 0px, Home/Profile/Withdrawals 16–20px, auth screens 24px) as each was built independently, which read as an inconsistent gap under the header when moving between them — measured now, every screen sits exactly 10px below the pill's bottom edge (2px clearance gap + 8px screen padding), no exceptions. Keep new screens on this same 8px top value rather than picking a fresh one.

## 5. Auth & second factor

Rebuilt this round against `api-integration.md` — see the top-of-file note for why (an incompatible earlier Telegram-binding architecture was fully replaced, not extended).

**A Telegram-identity-binding layer now sits on top of the email+password+OTP flow, backend-confirmed (not read off a Swagger file like everything else in this doc) — the third auth architecture this app has had.** Round 1 was a Telegram-binding `session.start`/`login`/`login-confirm` flow (`miniapp-auth-integration-spec.md`, deleted). Round 2 replaced it wholesale with `api-integration.md` §2's plain email+password+OTP-every-launch model, where `initData` was explicitly *not* an auth mechanism — just a one-shot header sent once after sign-in to bind `telegram_id` for push (`x-telegram-init-data`, `markInitDataBindPending()`). **Round 3, this one, replaces that one-shot header with a real binding flow** — conceptually closer to round 1, but a different concrete contract, given directly by the backend team rather than inferred from Swagger:

- New `real/miniAppAuth.ts`'s `authenticateMiniApp(initData, bearerToken?)` — `POST /telegram-mini-apps/{clientId}/authenticate` (`auth` service), `clientId` from `VITE_TELEGRAM_MINI_APP_CLIENT_ID` (env, never hardcoded). Two calling modes: no bearer = silent re-entry (binding already exists, returns a mini-app access token straight away); `Authorization: Bearer <platform JWT>` = creates the binding and returns the same shape. The platform JWT here is the OTP flow's own `/oauth2/token` result — `real/auth.ts`'s `signInConfirmOtp` now returns `{platformAccessToken}` instead of saving it as a session, since it's spent exactly once (as that Bearer) and discarded; the token that actually becomes the session is whatever `authenticateMiniApp` hands back. This orchestration — OTP confirm → spend the platform JWT → save the mini-app token — lives in `api/index.ts`'s `signInConfirmOtp` wrapper, not `SignIn.tsx` or `real/auth.ts`, specifically so both modes keep returning one `Session` shape and no screen needs a `USE_REAL_API` branch for it.
- **Every real-mode cold boot (`index.tsx`) tries `authenticateMiniApp(freshInitData)` silently, before ever rendering the login screen.** If this Telegram identity is already bound, a session appears with zero login/password/2FA — `SignIn.tsx` only renders because that came back empty-handed (genuinely unbound, or a transient failure; both are read the same way, see below). This is a real, awaited network call before `root.render(...)`, unlike round 2's fully synchronous boot — the app has no way to know if a launch is "first ever" or "the hundredth" without asking the backend first.
- **`tokenStore.ts` lost its refresh-token model entirely** — the mini-app OAuth client the backend registered explicitly has no refresh token. What used to be `refreshTokens()` calling `POST /oauth2/token` with a stored `refresh_token` is now a pluggable `reauthenticate` callback, wired once at boot (`setReauthenticator`) to `() => authenticateMiniApp(getFreshInitData())` — a lapsed access token gets replaced by silently re-running the exact same silent-boot call, not a grant exchange. No more `localStorage` refresh-token persistence either: the durable credential is the backend-side binding, discoverable fresh via `initData` on any device, any relaunch — not a secret this app has to keep safe locally. `sessionStorage`-restoring the access token itself is kept as a same-tab-reload optimization only (skips a network round trip on a plain page refresh).
- **`clientType` on a silent re-entry is a persisted client-side guess, not backend truth** — `lib/lastClientType.ts`, `localStorage`, defaults `UL`. Nothing in the profile response or the authenticate call carries an account-type field (`real/profile.ts`'s `getUser` already ignored its own `clientType` param for exactly this reason, pre-dating this round), so `clientType` has always been a display-only label in real mode, not a validated fact — this just persists the label across the moment (first bind) where it *was* known (whichever login screen variant the user actually completed) so silent re-entries later have something reasonable to show.
- **Two things are explicitly unconfirmed, isolated to one place each so a wrong guess is a one-line fix**: the success response's field names (assumed camelCase `accessToken`/`expiresIn`, `real/miniAppAuth.ts`) and the exact signal for "not bound yet" (any non-2xx here is read that way, rather than switched on a specific status/code — none was given). A **new, unresolved product question**: tapping "Выход" only clears local state (there's no documented revoke/unbind endpoint for this token) — since the binding itself persists server-side regardless, the very next boot's silent re-entry would immediately undo an explicit sign-out. Flagged in `real/auth.ts`'s `signOut` comment, not silently resolved either way.
- `x-telegram-init-data` and `markInitDataBindPending()` are gone outright, not just unused — deleted from `api/http.ts` and its one caller in `SignIn.tsx`, per explicit instruction.
- Social sign-in's `exchangeSocialCode` (already disabled, see below) used to save its own tokens into `tokenStore` directly — that call is gone too (the function it called no longer exists in the new token model); left returning the raw exchange result unsaved, flagged as unreconciled with this flow, not silently made to look like it still works.
- **Not verified end-to-end** — no Telegram context or live dev backend was reachable from this environment. Verified via `tsc`/lint/build plus a full mock-mode Playwright pass proving the (unaffected, `USE_REAL_API`-gated) mock boot path still renders and signs in cleanly. The real path needs an actual run inside Telegram against `https://api.dev.xruby.kg` to confirm.

**Two genuinely different "second factor" models now coexist, each with its own component** (unrelated to the binding layer above — this is about the standard login form's own OTP step, which still runs in full on a first-time bind):

- **Sign-in and password recovery — one second factor per account, never both at once.** Originally built as "always email/SMS OTP, *plus* an authenticator code when the account has one enabled" (a literal reading of §2.1's `twoFA` boolean) — **reversed by explicit product decision**: an account has exactly one method configured, and the modal should show that one field, mirroring how the withdrawal-confirmation `TwoFactorGate` trio already picks a single modal off an operation's `source` rather than stacking both. `OtpConfirmModal` (`src/screens/OtpConfirmModal/`, renamed and repurposed from the old Telegram-binding-era `LoginConfirmModal` it was adapted from — same shape, new internals) now renders exactly one `CodeInput`, titled/copy-branched by a new `source: 'email' | 'authenticator'` (`AuthOtpSource`, `api/types.ts`) — email gets the existing "Отправили код на {email}" + resend-with-countdown footer; authenticator gets `AuthenticatorModal`'s own title/body copy and no resend footer at all (an authenticator code isn't "sent" anywhere to resend). `SignIn.tsx`: `signInRequestOtp(email, password, clientType)` → `{transactionId, source}` → opens `OtpConfirmModal` → `signInConfirmOtp({transactionId, otp, email, clientType})` → `Session` — no more separate `twoFaCode` field anywhere, one `otp` field regardless of which source it came from. `PasswordRecovery.tsx` follows the identical shape. Mock fixtures: the business account (`UL`, `authenticatorEnabled: true`) gets `source: 'authenticator'`; the personal account (`FL`) gets `source: 'email'` — both branches exercisable without a dev switch, unchanged from before. Real mode's exact field name for this on `/oauth2/otp`'s response is unconfirmed (assumed to be `source`, matching the withdrawal OTP contract's own field of the same name and purpose) — isolated to `real/auth.ts`'s `signInRequestOtp`, one place to correct if the backend calls it something else. This incidentally fixed a latent bug in `PasswordRecovery.tsx`: its `handleOtpSubmit` only ever forwarded `{transactionId, otp}` to `recoveryConfirmOtp` (which never took a second code parameter), so a `twoFaCode` typed into the old always-both-fields modal was silently discarded for recovery specifically — moot now that there's only ever one field to fill.
- **Withdrawal confirmation — Google Authenticator *or* the email code, never both**, unchanged this round: `TwoFactorGate` picks one of `AuthenticatorModal`/`VerificationModal` based on `User.authenticatorEnabled`, both still call the old generic `sendVerificationCode`/`verifyCode` pair (now explicitly scoped to this use only — see `real/auth.ts`'s own comment). This is deliberately *not* yet wired to `api-integration.md` §5.3's real `issue-otp`/`confirm` endpoints — that's a Withdrawals-step task, not part of this round's Auth rewrite.
- Social sign-in (Google/Apple) skips both models — mock stays an instant fake session (`signInSocial`); real opens an external browser (`startSocialSignIn`) and completes best-effort on relaunch if the redirect is captured (`exchangeSocialCode`, checked once at boot in `index.tsx`) — §2.2 flags this as best-effort for MVP (question B3), not blocking. **Temporarily hidden from `SignIn.tsx` entirely** (`SOCIAL_AUTH_ENABLED = false`, a local constant, both buttons and their wrapping row) — no real contract for it exists yet and the test plan's own B3 question asks whether social sign-in should just stay off for the mini app. All the wiring above is untouched underneath; flip the flag back once the API lands.
- Both `CodeInput`-based modal families share the same responsive `CodeInput` (§3).

The two fields can never hold the same account — picking one flips the other; the swap button exchanges them and leaves the asset/amount alone.

The ring's vertical position is **measured off the DOM, not guessed from a CSS midpoint.** Centering it at 50% of the whole `С`-label+box+`На`-label+box stack lands it much closer to `С` than to `На`, because only `На` has a label sitting in the way — it read as "pinned to the top field" rather than symmetric. `TransferModal.tsx` instead measures the actual `.select__box` elements' `getBoundingClientRect()` (via a `ResizeObserver` on the accounts container, plus a one-off re-measure ~220ms after open to let the modal's scale-in animation settle first — measuring mid-animation was itself good for a few stray px) and sets the ring's `top` to the true midpoint between "С" box's bottom and "На" box's top. This is deliberately dynamic rather than a hardcoded px offset so it stays correct if the label text, font, or locale ever changes.

**Spacing rhythm — three different gaps, not normalized to one.** 8px between the `С` and `На` field groups (the swap ring straddles this seam). **40px** between the account block and the amount block (`Списать`) — they're separate blocks and the frame draws the separation that way. 12px between the two footer buttons (`.transfer-modal__footer`, not the shared `.button-row`'s default 16px). Do not collapse these to a single uniform gap.

**Amount field.** Standard `AmountField` (44px, `--bg-page` fill — the one place besides the account selects where a field's fill matters: `--bg-elevated` means "pick a thing", `--bg-page` means "type a number"), with an embedded 24px `CurrencyIcon` asset `Select` and a "Макс" button. A transfer carries no fee, so "Макс" is the full available balance of the source account for the selected asset.

**Footer.** Paired `Отменить` (secondary) / `Подтвердить` (accent) buttons, 12px gap (see above).

**Behaviour** (unchanged by the rebuild): on confirm, the modal closes, a toast confirms, and the screen underneath re-fetches balances — which on the deal hold-confirmation screen can move the callout into a different case, the reason the transfer glyph is reachable from there at all. **Wired for real this round** (`api-integration.md` §6, `real/transfers.ts`): `POST /operations/transfer/internal` with `{currency, accountFrom, accountTo, amount}`, empty 200, no OTP step. The catch: `accountFrom`/`accountTo` are the backend's *own* account keys, not the app's `deposit`/`trading` labels `getAccounts()` remaps them to for display (§6.5/§8) — a new `resolveTransferAccounts()` in `real/balances.ts` maps back from the app's labels to the real keys, reusing the same positional first/second-key convention (question B7) the rest of that file already uses, rather than inventing a second guess at which key is which.
